# PR 5: Source patches

Branch `pr5-source-patches`, off `main` (`eb353af`). Follows Fable's review of PR #3: the profile collision and the
executable version resource. No build was run and nothing was installed.

## What

- `patches/0001-profile-folder-orbis.patch`: adds `imply_option("MOZ_APP_PROFILE", "Orbis")` to
  `browser/moz.configure`. `application.ini` then gets `Profile=Orbis`, and Windows profiles live in
  `%APPDATA%\Orbis` and `%LOCALAPPDATA%\Orbis` instead of `%APPDATA%\Mozilla\Firefox` and
  `%LOCALAPPDATA%\Mozilla\Firefox`. `MOZ_APP_PROFILE` is a `project_flag`, so no mozconfig option can set it.
- `patches/0002-version-resource-orbis.patch`: `browser/app/module.ver` (`orbis.exe`),
  `browser/app/pbproxy/module.ver` (`private_browsing.exe`) and `ipc/app/module.ver` (`plugin-container.exe`):
  `CompanyName` "Mozilla Corporation" becomes "Orbis", and `LegalTrademarks` ("Firefox is a Trademark of The
  Mozilla Foundation.", or the `create_rc.py` default "Mozilla" for plugin-container) becomes empty.
  `FileDescription` and `ProductName` already resolve to "Orbis" through `@MOZ_APP_DISPLAYNAME@`, so they are not
  patched. `LegalCopyright` is left as is (a true statement about the code's authors).
- `scripts/apply-patches.ps1`: applies `patches\*.patch` in order with `git apply`, after `git apply --check` of the
  whole series. Refuses a checkout off `C:`, inside this repository, through a junction (anywhere on its path), not
  a Firefox git checkout, not at the pinned commit, or with changes to tracked files. Untracked overlay files are
  fine. If exactly these patches are already applied, it says so and exits 0. `-Check` writes nothing.
- `docs/PATCHES.md`: each patch, why no setting can do it, why `--with-app-basename` must stay `Firefox`, the test
  plan, and what is still shared with Firefox.
- `.gitattributes`: `patches/** -text`, so Git never rewrites patch bytes (`ipc/app/module.ver` has CRLF upstream,
  and the `©` in the context lines is the single Latin-1 byte `0xA9`, as in Mozilla's file).
- `docs/UPDATING.md`: `apply-patches.ps1 -Check` is a step when the pin moves. `AGENTS.md`, `README.md`: map.

## Why not `--with-app-basename=Orbis`

`Services.appinfo.name` is the basename. `nsHttpHandler.cpp` adds the `Firefox/160.0` user-agent token only when
the app name is `Firefox`, so the user agent would end in `Orbis/160.0` (every Orbis user stands out, sites that
check for Firefox break). `SearchEngineSelector.sys.mjs` passes `Services.appinfo.name` to the search
configuration, so the built-in engine list would change. The profile name is the narrowest fix.

MSIX is not a fix by itself: Firefox expects to share `profiles.ini` and `installs.ini` when packaged
(`nsXREDirProvider::GetInstallHash` hashes the package family name; `MaybeMakeDefaultDedicatedProfile` runs as
usual).

## Still shared with Firefox

`EnterprisePoliciesParent` reads `SOFTWARE\Policies` under HKCU then HKLM, and `WindowsGPOParser` opens
`Mozilla\` + `Services.appinfo.name`. So Orbis reads **`HKLM\SOFTWARE\Policies\Mozilla\Firefox`** (and the HKCU
twin): an administrator's Firefox group policies also apply to Orbis. Documented, not fixed (it needs the basename
or a patch to `WindowsGPOParser`); it only matters on managed PCs.

## Test plan (needs a build)

On a test PC or VM with Firefox installed and used, not on Shibi's PC: hash `%APPDATA%\Mozilla\Firefox\profiles.ini`
and `installs.ini` and list both Mozilla folders; install and run Orbis twice; both `.ini` files must be
byte-identical, nothing in the Mozilla folders may change, and Orbis's profile must be under `%APPDATA%\Orbis` and
`%LOCALAPPDATA%\Orbis` (or the MSIX-virtualised equivalents). Then Firefox must open its own profile with no prompt,
and each program must open its own window while the other runs. Version resource: `(Get-Item orbis.exe).VersionInfo`
shows `CompanyName` Orbis and no Firefox trademark line, also for `private_browsing.exe` and `plugin-container.exe`.
Full steps in `docs/PATCHES.md`.

   ```
   git -c core.autocrlf=false apply --check --verbose patches/0002-version-resource-orbis.patch  -> OK

   ```

   Applied there: `imply_option("MOZ_APP_PROFILE", "Orbis")` sits after the vendor line; the three `module.ver`
   files parse (same split as `create_rc.parse_module_ver`) to `CompanyName` Orbis and an empty
   `WIN32_MODULE_TRADEMARKS`; `ipc/app/module.ver` keeps CRLF on all 7 lines.

   the pinned commit, with a pin file naming its HEAD):
   - real `upstream/firefox.json` (wrong commit): `REFUSED`, exit 1;
   - `-Check` with untracked `mozconfig` and `browser\branding\orbis`: `OK (check only)`, exit 0, nothing changed;
   - apply: `OK: applied 2 patches`, exactly the four files changed, identical to the plain `git apply` result;
   - again: `OK: all 2 patches are already applied; nothing written`;
   - patched plus one extra line in a patched file: `REFUSED` (dirty, not exactly our patches); restored: already
     applied, exit 0;
   - another tracked file changed (`mach`): `REFUSED`, exit 1;
   - source drifted (vendor line changed and committed, pin moved to it): `REFUSED: git apply --check failed;
     nothing applied`, exit 1, tree unchanged;
   - checkout inside this repository, checkout on `D:`: `REFUSED`, exit 1.
   - No scratch folder left behind in `%TEMP%`.
3. `apply-patches.ps1` is ASCII and parses in Windows PowerShell 5.1.
